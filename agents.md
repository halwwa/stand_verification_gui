# Руководство для AI-агентов

## Обзор проекта

`stand-verification` — настольное GUI-приложение на Python для автоматизированной поверки радиоприборов. Программа управляет СК3-50, С6-22 и генератором R&S SMB100A, выполняет 12 поверочных тестов, показывает статусы и журнал, а результаты сохраняет в Excel.

Основная платформа — Windows 10/11. В README указан Python 3.11+, GitHub Actions использует Python 3.12; локально проект проверялся и на Python 3.14. В `pyproject.toml` поле `requires-python` не задано. GUI построен на `tkinter`/`ttk`; отдельного веб-интерфейса, CLI для измерений или серверного компонента нет.

Актуальный прикладной код находится в пакете `stand_verification/`. Каталог `legacy/` содержит исходные автономные сценарии, от которых произошла часть измерительной логики; они не входят в собираемый пакет. Не изменяйте текущие допуски и последовательности команд только ради приведения их к более «общему» виду: многие детали намеренно сохранены из старых сценариев.

## Зависимости и конфигурационные файлы

- `pyproject.toml` — setuptools-пакет `stand-verification` версии 0.1.0. В пакет включаются только каталоги `stand_verification*`. Рабочие зависимости: `pyserial`, `pyvisa`, `pyvisa-py`, `openpyxl`.
- `requirements.txt` — более широкий список для запуска из исходников: дополнительно содержит `matplotlib`, `numpy`, `pandas` и `seaborn`. Основной пакет эти библиотеки не импортирует.
- `.github/workflows/build-windows.yml` — ручная сборка Windows EXE.
- `.gitignore` — исключает кэши Python, виртуальные окружения, `build/`, `dist/`, `*.spec`, `*.xlsx`, журналы, `*.egg-info/` и `config.json`.
- `stand_verification/config.py` — частоты, уровни, полосы фильтров, задержки, допуски, идентификаторы тестов и параметры подключения по умолчанию. Внешних переменных окружения приложение не использует.
- `stand_verification/ui/user_config.py` — сохраняет последние COM/LAN-параметры и выбранный тип подключения СК3-50 в `config.json`: рядом с EXE либо в корне проекта при запуске из исходников. Ошибки чтения/записи этого файла намеренно подавляются.

Версии зависимостей не закреплены lock-файлом. `tkinter` поставляется с Python, а не устанавливается через pip. PyInstaller не объявлен в зависимостях проекта и устанавливается отдельно.

## Установка и запуск

Для установки только рабочих зависимостей пакета:

```bat
python -m pip install .
```

Для установки полного списка из README:

```bat
python -m pip install -r requirements.txt
```

Оба способа запуска ведут в `stand_verification.ui.app.main`:

```bat
python gui_stand.py
python -m stand_verification
```

`gui_stand.py` — тонкий launcher для исходников и PyInstaller. Консольная entry point в `pyproject.toml` не объявлена. Импорт entry point не должен создавать окно; окно создаётся только при вызове `main()`.

По умолчанию используются:

- СК3-50: COM, 115200 бод; также доступен LAN через raw TCP socket (IP задаётся пользователем, порт по умолчанию 5025);
- С6-22: COM, 9600 бод;
- SMB100A: `192.168.0.113`, TCP-порт 5025;
- путь отчёта: `C:/Reports/Calibration/2026/`.

Для реального прогона обязательно подключены СК3-50 и SMB100A. С6-22 нужен только для тестов 7 и 8; без него эти тесты пропускаются с сообщением в журнале.

### Приборный слой

`DeviceCard` открывает соединения в отдельном потоке. Список COM-портов обновляется каждую секунду при изменении, кнопкой «↻», при раскрытии списка и перед подключением; введённый вручную порт сохраняется. Для СК3-50 доступен переключатель COM/LAN, тип подключения сохраняется в `config.json`.

`open_serial()` создаёт `serial.Serial(..., timeout=2)`, отправляет `*IDN?` и повторяет чтение при пустом ответе. `open_socket()` использует `socket.create_connection(..., timeout=2)`, затем устанавливает `sock.settimeout(10)` и работает через `makefile('rwb')`, предоставляя СК3-50 тот же интерфейс `write/flush/readline`, что и serial. `open_visa()` использует backend `ResourceManager('@py')`, ресурс `TCPIP::<host>::<port>::SOCKET`, timeout 5000 мс и перевод строки `\n`.

Классы `SK350`, `C622` и `SMB100A` получают уже открытую сессию и не владеют её жизненным циклом. Закрытие выполняет вызывающий код через `close_resources()`. В GUI порядок карточек значим: `cards[0]` — СК3-50, `cards[1]` — С6-22, `cards[2]` — SMB100A.

`MeasurementEngine` принимает либо эти адаптеры, либо низкоуровневые сессии и при необходимости оборачивает их сам. Благодаря этому тесты передают простые fake-сессии с `write`, `query`, `readline` и `flush`.

### Движок измерений

Идентификаторы тестов задаются в `config.py`; `NOT_IMPLEMENTED` сейчас пусто, реализованы все 12 тестов:

1. `frequency.py` — погрешность частоты.
2. `level.py` — погрешность уровня.
3. `am_noise.py` — АМ шум.
4. `fm_noise.py` — ЧМ шум.
5. `pm_noise.py` — ФМ шум.
6. `am_fm_transition.py` — переход АМ↔ЧМ.
7. `thd_am.py` — КГ АМ, требуется С6-22.
8. `thd_fm.py` — КГ ЧМ, требуется С6-22.
9. `fm_linearity.py` — линейность шкал ЧМ.
10. `fm_deviation.py` — погрешность пиковых значений девиации ЧМ.
11. `am_peaks.py` — погрешность пиковых значений Кам.
12. `pm_peaks.py` — погрешность пиковых значений индекса ФМ.

Тесты 1–5 выполняются внутри общего цикла по `F_LIST`; затем последовательно запускаются отдельные сценарии 6–12. Движок заранее вычисляет план точек (`_planned`), обновляет progress callback, собирает результаты по идентификаторам тестов и формирует `summary()`.

При инициализации генератор получает `*RST`, `OUTP ON`, `FREQ 10 MHz`, `POW -13`. В `finally` после начатой инициализации движок всегда пытается отправить `OUTP OFF`, включая ошибки и остановку. Ошибка выключения переводит итог в `error`; GUI оставляет соединения и окно открытыми и предлагает «Повторить OUTP OFF». Команда подтверждает только успешную отправку запроса, а не фактическое аппаратное выключение.

`snapshot()` возвращает `RunSnapshot` с глубокими копиями результатов и сводки. Это отделяет уже сформированный отчёт от последующих прогонов и изменений движка.

### Потоки и GUI

Главный поток должен оставаться единственным потоком, обращающимся к Tk-виджетам. Worker-потоки подключения и измерений помещают замыкания в `queue.Queue`; `StandApp._drain_callbacks()` выполняет их через `root.after(50, ...)`. Не вызывайте `log()`, `messagebox`, `StringVar.set()` или другие Tk-операции напрямую из worker-потока.

Остановка кооперативная: общий `threading.Event` проверяется в движке и сценариях, а `stop_event.wait(timeout)` используется вместо непрерываемого `sleep()` для большинства измерительных выдержек. При провале `confirm_callback` синхронно спрашивает оператора, продолжать ли прогон; предупреждения такого диалога не вызывают.

При закрытии GUI ждёт завершения worker-потоков и очистки очереди, затем отключает приборы. Отчёт сохраняется даже после ошибки или частичной остановки. Если основной путь недоступен, приложение пытается сохранить файл в текущем каталоге через `os.path.join('.', fname)`.

## Модели, единицы и статусы

Все результативные dataclass в `models.py` помечены `frozen=True`. Поля измерений, которые не удалось получить, обычно равны `None`; не подменяйте их нулём.

Единицы закреплены именами полей: частоты генератора обычно задаются в МГц, команды девиации — в Гц, а результаты тестов 9 и 10 хранятся в кГц. Перед изменением формул сверяйте единицы с моделью, заголовками Excel и соответствующим legacy-сценарием.

`tolerances.evaluate(value, tolerance)` возвращает кортеж `(статус, emoji)`:

- `fail` / `ПРОВАЛ`, если `abs(value) > tolerance`;
- `warn` / `ВНИМАНИЕ`, если `abs(value) > 0.7 * tolerance`, но не `fail`;
- `ok` / `OK` в остальных случаях.

Граница ровно 70% ещё считается `ok`, граница ровно 100% — `warn`. `NaN` и бесконечности отклоняются через `require_finite()`.

Статусы строк: `ok`, `warn`, `fail`, `error`. Итоговые статусы движка: `not_started`, `done`, `warn`, `stopped`, `error`; в сводке отдельных тестов также встречается `incomplete`. Эти строки используются GUI и Excel, поэтому их нельзя менять изолированно в одном модуле.

## Стиль кода

- Следуйте существующему стилю Python: 4 пробела, `snake_case` для функций и переменных, `PascalCase` для классов, верхний регистр для констант.
- Пользовательские сообщения, журнал и большинство комментариев — на русском. Сохраняйте русскую терминологию и единицы измерения.
- Новые результаты должны соответствовать существующим frozen dataclass и явным полям с единицами.
- Драйверы должны оставаться тонкими адаптерами команд; не переносите в них открытие/закрытие соединения или orchestration тестов.
- Не добавляйте импорты `tkinter`, `serial`, `pyvisa` или `openpyxl` в модуль движка: тесты специально проверяют независимость импорта measurement-слоя от GUI, аппаратных библиотек и Excel.
- Форматтер, линтер, type checker и их настройки в проекте не заданы. Не считайте Black, Ruff, mypy или pytest обязательными без отдельного решения.

## Тестирование

Стандартный запуск из корня:

```bash
python -m unittest discover -s tests -v
```

Тесты используют `unittest`, `unittest.mock`, fake-сессии и fake stop event; реальные приборы и открытие GUI-окна не нужны. Excel-тесты пишут во временные каталоги. Для новых сценариев сохраняйте этот подход: мокайте приборный ввод-вывод и задержки, проверяйте команды, частичные результаты, статусы, повторный запуск и обязательный `OUTP OFF`.

Особенно важны characterization-тесты:

- `test_devices.py`, `test_device_card.py` — точные параметры соединений, команды адаптеров, raw socket, переключение COM/LAN и обновление списка портов;
- `test_engine_characterization.py`, `test_measurement_engine.py` — порядок команд, остановка, ошибки, сводка и неизменяемость snapshot;
- `test_excel_characterization.py` — листы, значения, цвета и повторное сохранение;
- `test_imports.py` — границы импортов и отсутствие окна при импорте;
- `test_ui_lifecycle.py` — fallback отчёта и безопасное закрытие;
- `test_level_tolerance.py`, `test_thd_fm.py` — границы и формулы допусков.

Состояние на момент написания (локальный прогон под Windows, Python 3.14.5): выполняется 59 тестов, проходят 55, падают 4:

- `EngineCharacterizationTests.test_combined_command_and_query_order_includes_double_frequency_query`: движок дополнительно отправляет `POW -13` перед измерением уровня (долгоживущее расхождение);
- `MeasurementEngineTests.test_rerun_does_not_mutate_prior_snapshot`: тест ожидает старый comment `🟢`, а `evaluate()` сейчас возвращает `OK` (долгоживущее расхождение);
- `DeviceCard.SocketConnectionTests.test_socket_idn_uses_raw_tcp_session_and_retries_empty_answer`: тест ожидает `settimeout(2)`, а в рабочем дереве `open_socket()` выставляет `settimeout(10)` (несовмещённое с тестом незакоммиченное изменение);
- `UiLifecycleTests.test_failed_primary_export_uses_fallback_without_rerunning_engine`: тест ожидает путь `'./run.xlsx'`, а код возвращает `'.\\run.xlsx'` через `os.path.join('.', fname)` — различие разделителей путей Windows/Linux.

Перед исправлением кода отличайте эти известные failures от новых регрессий. Не «чините» characterization-ожидания без проверки требуемого поведения прибора.

Полный GUI и работа с реальными приборами автоматически не проверяются. Аппаратный прогон требует отдельной контролируемой проверки на стенде.

## Excel и локальные данные

`export_excel()` создаёт отдельный лист для каждого выбранного теста и служебные листы `Сводка`, `Тесты`, `Диагностика`. При повторном сохранении в существующий файл управляемые листы удаляются и создаются заново, а посторонние листы сохраняются. Поэтому не используйте без необходимости чужой рабочий файл как цель экспорта и не меняйте этот контракт незаметно.

`config.json` содержит локальные адреса, порты и скорости подключения. Файл перечислен в `.gitignore` — не добавляйте его, отчёты и журналы в коммиты.

## Сборка и публикация

Автоматическая сборка запускается только вручную через `workflow_dispatch` в GitHub Actions, на `windows-latest` с Python 3.12. Эффективные команды workflow:

```bat
python -m pip install .
python -m pip install pyinstaller
python -m PyInstaller --clean --noconfirm --onefile --windowed --collect-all pyvisa_py --name StandVerification gui_stand.py
```

Результат `dist/StandVerification.exe` загружается как artifact `StandVerification-Windows`. В workflow нет шага тестирования, релиза или развёртывания на машины пользователей.

README также содержит отдельную ручную команду с именем `StandGUI`, `--collect-all` для `pyvisa`, `pyvisa_py`, `serial`, `openpyxl`, скрытым импортом `serial.tools.list_ports`, `--add-data "stand_verification;stand_verification"` и исключением тяжёлых научных библиотек. Её результат — `dist/StandGUI.exe`. Не смешивайте имена и параметры этих двух команд; при изменении упаковки синхронно обновляйте README и workflow.

## Безопасность и работа с оборудованием

- Не запускайте измерительные сценарии на реальном стенде ради обычной проверки изменений: они сбрасывают генератор, включают RF-выход и меняют режимы приборов.
- Используйте mocks/fakes в автоматических тестах. Для аппаратной проверки нужны правильные соединения и контроль фактического состояния выхода.
- Сохраняйте попытку `OUTP OFF` на всех путях завершения и возможность повторить её при ошибке.
- Не закрывайте соединения, пока активны worker-потоки или не разрешена ошибка выключения генератора.
- Учитывайте долгие реальные выдержки и калибровки; в тестах их следует заменять fake event/patch, а не удалять из рабочего сценария.

## Git workflow

- Делайте коммиты небольшими, сфокусированными и логически атомарными.
- Один коммит должен представлять одно цельное изменение; не смешивайте рефакторинг с функциональными изменениями.
- Используйте ясные описательные сообщения коммитов на русском, как в существующей истории.
- Не выполняйте amend, squash, rebase и переписывание существующих коммитов без явного запроса.
- Не отправляйте изменения в remote и не создавайте pull request без явного запроса пользователя.
- Не меняйте git remotes и настройки репозитория.
- Если задача состоит из независимых завершённых шагов, предпочтительно коммитить каждый шаг перед переходом к следующему.
- Не создавайте коммит из незавершённого, сломанного или промежуточного состояния, если сохранение такого состояния не требуется для задачи.
